# Звонки Finchat: пошаговая инструкция для мобильного приложения

Инструкция описывает текущий клиентский контракт: какие команды отправлять,
какие ответы ждать и как управлять экраном звонка. Примеры — для WebSocket.
Схемы полей доступны в [swagger.yaml](swagger.yaml).

## 1. Какие соединения используются

| Назначение | Способ подключения |
|---|---|
| Вход в Finchat, приглашения и управление звонками | Существующее соединение Finchat WebSocket/gRPC |
| Звук, видео, события медиасоединения и участников | LiveKit SDK |
| Регистрация отдельного PushKit-токена iOS | HTTPS API Finchat |
| Входящий вызов в фоне | Android FCM / iOS PushKit |

**Команды `/calls/start`, `/calls/join` и остальные `/calls/*` в Swagger — виртуальные
операции документации. Делать HTTP POST по этим адресам нельзя.** Отправляйте
показанный JSON в существующее соединение Finchat.

HTTPS-методов получения и обновления LiveKit JWT сейчас нет. JWT приходит приватным
сообщением Finchat. Не отправляйте токен Finchat на адрес LiveKit.

Для gRPC используйте сообщения существующей схемы Finchat, а JSON из `note.payload`
передавайте в поле payload. Значения событий: `ACCEPT`, `RINGING`, `HANG_UP`;
входящее приглашение — `INVITE`.

### Что получить перед началом разработки

- HTTPS-хост Finchat и его WebSocket-адрес.
- API key приложения Finchat для открытия соединения.
- Тестовую учётную запись и обычный токен входа Finchat.
- Настройки FCM и, для iOS, PushKit/CallKit для вашего приложения.

API key приложения Finchat — не API key LiveKit. Секреты LiveKit и Apple
мобильному приложению не нужны. LiveKit URL берите из ответа с JWT, а не из константы.

В примерах `usrPeer`, `usrCaller`, `grpTeam`, JWT и остальные идентификаторы условные.
Для реальных запросов подставляйте значения своего окружения.

## 2. Идентификаторы: что хранить на клиенте

| Поле | Для чего использовать |
|---|---|
| `topic` | Чат: `usr…` собеседника или `grp…` группы |
| `seq` | Номер исходного сообщения звонка; передаётся во всех командах этого звонка |
| `callId` | UUID звонка; ключ состояния UI, системного вызова и дедупликации push |
| `requestId` | Уникальный идентификатор конкретной команды `note` |
| `pub.id` | Идентификатор команды создания звонка или обычного сообщения |
| `version` | Версия уведомления в рамках `callId` |
| `room` | Имя комнаты LiveKit из ответа с JWT |
| `identity` | Идентификатор участника LiveKit вида `usrUser:FinchatSessionID` |

Для управления звонком храните одновременно `callId`, `topic` и `seq`.
Нельзя передавать UUID `callId` вместо числового `seq`.

Полная `identity` меняется при смене Finchat-сессии. Для поиска имени и аватара
используйте Finchat user ID — часть `identity` до первого `:`. В push аватара нет:
берёте его из кеша профилей либо показываете заглушку.

Профили, чат и звонки не должны зависеть от наличия JWT в постоянном хранилище.
JWT не логируйте и не передавайте другим участникам.

## 3. Подготовка: соединение и авторизация

### Шаг 3.1. Открыть WebSocket Finchat

```text
wss://<FINCHAT_HOST>/v0/channels?apikey=<FINCHAT_APP_API_KEY>
```

Если приложение уже авторизовано и имеет рабочее соединение, используйте его.
В окружении с нестандартным префиксом API уточните полный адрес у команды проекта.

### Шаг 3.2. Отправить `hi`

Для iOS:

```json
{
  "hi": {
    "id": "hi-1",
    "ver": "0.22",
    "ua": "Finchat iOS",
    "lang": "ru-RU",
    "platf": "ios",
    "dev": "CURRENT_FCM_TOKEN"
  }
}
```

Для Android укажите `platf: "android"` и соответствующий `ua`.
`hi.dev` — обычный FCM-токен, **не PushKit-токен**.
Используйте поддерживаемую вашей версией приложения версию протокола.

Дождитесь успешного `ctrl` с соответствующим `id`. Проверьте возможности в
`ctrl.params`; пример фрагмента:

```json
{
  "calls": {
    "provider": "livekit",
    "group": true,
    "maxParticipants": 50,
    "notificationsVersion": 2,
    "commandsVersion": 2,
    "groupNotifications": "notify",
    "callWaiting": true,
    "waitingAction": "end-and-accept"
  },
  "callTimeout": 30
}
```

Если `calls.provider` не равен `livekit`, не запускайте описанный здесь сценарий.
`callTimeout` — срок ожидания ответа, не максимальная длительность разговора.
Значения лимитов и режим группы берите из handshake.

### Шаг 3.3. Войти с сохранённым токеном Finchat

```json
{
  "login": {
    "id": "login-1",
    "scheme": "token",
    "secret": "BASE64_FINCHAT_LOGIN_TOKEN"
  }
}
```

В JSON используется Base64-представление токена входа. Если оно уже получено
в таком виде из login-ответа, не кодируйте строку повторно.
Дождитесь успешного `ctrl` для `login-1`. При истёкшем токене выполните обычный
сценарий входа приложения, затем вернитесь к подготовке звонков.

### Шаг 3.4. Подписаться на `me`

```json
{"sub":{"id":"sub-me-1","topic":"me"}}
```

Дождитесь успешного ответа. Через `me` приходят приглашения и управляющие уведомления.
Установите общий обработчик таких сообщений до начала звонка.

### Шаг 3.5. Подписаться на нужный чат

Перед исходящим звонком:

```json
{"sub":{"id":"sub-chat-1","topic":"usrPeer"}}
```

Для группы замените `usrPeer` на `grpTeam`. Если подписка уже активна, повторять её
не нужно. После восстановления соединения восстановите подписку перед `status`.
Для показа входящего приглашения загружать историю чата не требуется.

## 4. Однократная настройка push на устройстве

### Android

1. Получить FCM-токен и зарегистрировать его обычным способом через `hi.dev`.
2. Обрабатывать FCM `data.what == "call"` отдельным обработчиком звонков.
3. Создавать системное уведомление/интерфейс вызова на стороне приложения:
   автоматического `notification`-блока у call-push нет.
4. При ротации FCM-токена обновлять регистрацию устройства.

### iOS

1. Зарегистрировать обычный FCM-токен через `hi.dev` с `platf: "ios"` и выполнить вход.
2. Получить отдельный device token через PushKit и преобразовать его в hex-строку.
3. Выполнить реальный HTTPS-запрос на хост **Finchat**, не LiveKit:

```http
PUT /v0/calls/devices/voip
Authorization: token BASE64_FINCHAT_LOGIN_TOKEN
Content-Type: application/json

{"device":"CURRENT_FCM_TOKEN","token":"HEX_PUSHKIT_DEVICE_TOKEN"}
```

Успех — `204`, без тела ответа. Префикс авторизации — точно `token ` в нижнем регистре,
не `Bearer `. Альтернатива — заголовок `X-Finchat-Auth` с тем же значением.

4. При изменении FCM- или PushKit-токена повторить регистрацию с актуальной парой.
5. Перед выходом из аккаунта, пока обычное устройство ещё зарегистрировано, удалить
   привязку тем же телом:

```http
DELETE /v0/calls/devices/voip
Authorization: token BASE64_FINCHAT_LOGIN_TOKEN
Content-Type: application/json

{"device":"CURRENT_FCM_TOKEN","token":"HEX_PUSHKIT_DEVICE_TOKEN"}
```

Затем выполнить обычный выход из аккаунта и очистку локального состояния звонков.

Ошибки регистрации: `400` — неверные данные, `401` — авторизация, `403` — обычный
FCM-токен не зарегистрирован за этим пользователем, `503` — временная ошибка.
Ответы ошибок этого HTTP API — текст, не Finchat `ctrl`.

## 5. Исходящий личный звонок

### Шаг 5.1. Подготовить локальный UI и разрешения

Проверьте доступ к микрофону, для видео — к камере. Если разрешения отсутствуют,
не создавайте звонок, который приложение не сможет обслужить.
Создайте локальное состояние исходящей попытки с уникальным `pub.id`.

### Шаг 5.2. Отправить команду начала

```json
{
  "pub": {
    "id": "start-1",
    "topic": "usrPeer",
    "head": {
      "webrtc": "started",
      "aonly": true
    },
    "content": "Аудиозвонок"
  }
}
```

Для видео передайте `aonly: false`. Не создавайте вторую команду `pub` для получения
или обновления JWT текущего звонка.

### Шаг 5.3. Обработать два независимых ответа

Первый вид ответа — `ctrl` с `id: "start-1"`. При успехе сохраните `ctrl.params.seq`.
Второй — приватный `info` с токеном:

```json
{
  "info": {
    "topic": "usrPeer",
    "what": "call",
    "event": "accept",
    "seq": 123,
    "payload": {
      "type": "token",
      "requestId": "start-1",
      "provider": "livekit",
      "url": "wss://call.finchat.club",
      "token": "LIVEKIT_JWT",
      "room": "fc-example-room",
      "identity": "usrMe:sessionId",
      "expiresIn": 60,
      "callId": "663e26ca-50cc-5965-8478-12ff882d1968",
      "version": 4
    }
  }
}
```

Не рассчитывайте на конкретный порядок сообщений. Ответ с токеном сопоставляйте
по `payload.requestId`, а не только по внешнему `event: "accept"`.
Если создание подтвердилось, но токен не пришёл или пришла ошибка его получения,
не начинайте новый звонок: запросите `status` и затем `join` существующего.

### Шаг 5.4. Подключить LiveKit SDK

1. Подключиться к `payload.url` с `payload.token`.
2. Включить публикацию микрофона; камеру — только для видеозвонка и с разрешением пользователя.
3. Подписаться на события участников, треков, подключения и переподключения SDK.
4. Показать исходящий вызов с ожиданием ответа.

Инициатор может подключиться до ответа собеседника. Подключение к комнате,
в которой пока нет собеседника, не означает, что тот ответил.
Не показывайте badge сквозного шифрования: ключи E2EE этот контракт не предоставляет.

### Шаг 5.5. Обработать ответ собеседника

- `ringing` — собеседнику показан входящий экран.
- `payload.event: "accepted"` — приглашение принято; прекратите сигнал ожидания,
  покажите подключение, пока SDK не подтвердит наличие нужных участников/треков.
- `cancelled` с `reason: "declined"` — отказ.
- `cancelled` с `reason: "missed"` — вызов закрыт без ответа.
- `ended` — завершить звонок и отключить SDK.

Для длительности разговора используйте подтверждённое медиасоединение, а не момент
отправки `pub` или получения JWT. После разговора итоговая длительность доступна в истории.

## 6. Входящий звонок

### Шаг 6.1. Принять приглашение из любого канала

Пример Finchat-события:

```json
{
  "info": {
    "topic": "me",
    "src": "usrCaller",
    "from": "usrCaller",
    "what": "call",
    "event": "invite",
    "seq": 123,
    "payload": {
      "callId": "663e26ca-50cc-5965-8478-12ff882d1968",
      "event": "invite",
      "version": 1,
      "topic": "usrCaller",
      "seq": 123,
      "from": "usrCaller",
      "title": "Алексей",
      "audioOnly": true,
      "group": false,
      "ring": true,
      "createdAt": "2026-10-16T12:00:00Z",
      "expiresAt": "2026-10-16T12:00:30Z"
    }
  }
}
```

Даты — пример формата; в приложении проверяйте актуальный `expiresAt` события.

Каналы доставки имеют разную оболочку, но одинаковый смысл:

| Канал | Где лежат поля |
|---|---|
| Finchat | `info.payload`; чат дополнительно находится в `info.src` |
| Android FCM | `data`, признак `what: "call"`; все значения строковые, отправитель — `xfrom` |
| iOS PushKit | В корне JSON рядом с `aps`; признак `what: "call"`, отправитель — `from` |

В FCM преобразуйте `seq` и `version` в числа, `audioOnly`, `group`, `ring` — в boolean,
время — из RFC 3339. Не используйте проверку «непустая строка» для boolean:
строка `"false"` должна означать false.

### Шаг 6.2. Проверить приглашение и показать UI

1. Найти локальное состояние по `callId`.
2. Отбросить повтор или устаревшую версию уведомления.
3. Не открывать заново уже закрытый входящий вызов по запоздалому `invite`.
4. Проверить `expiresAt`; просроченное приглашение не показывать как актуальный вызов.
5. При `ring: true` показать входящий вызов; при `ring: false` — уведомление
   о начавшемся групповом звонке без обычного входящего рингтона.
6. Поставить локальный таймер до `expiresAt`, чтобы закрыть неотвеченный вызов
   даже без получения push отмены.

Для iOS обработчик PushKit должен быть интегрирован с CallKit. Не откладывайте
обработку системного вызова до загрузки истории, профиля или сетевого `status`.
Если при сверке выяснилось, что вызов уже не актуален, завершите соответствующий
системный вызов. Дедупликация не заменяет требования жизненного цикла PushKit/CallKit.

Входящий UI можно показать без загрузки чата. Если соединения Finchat нет,
параллельно восстановите его, авторизацию и подписки. Не подключайтесь к LiveKit
до осознанного принятия приглашения пользователем.

### Шаг 6.3. Сообщить о показе входящего

Когда соединение Finchat готово и UI показан:

```json
{
  "note": {
    "topic": "usrCaller",
    "what": "call",
    "event": "ringing",
    "seq": 123,
    "payload": {"requestId": "ring-1"}
  }
}
```

Это только подтверждение показа, не принятие звонка. Не повторяйте его на каждую
копию push. Уведомление `ringing`, получаемое звонящим, не содержит `callId`:
сопоставляйте его по `info.src + info.seq`.

### Шаг 6.4. Принять звонок

После нажатия «Ответить»:

```json
{
  "note": {
    "topic": "usrCaller",
    "what": "call",
    "event": "accept",
    "seq": 123,
    "payload": {"action": "join", "requestId": "join-1"}
  }
}
```

1. Дождаться приватного `info.payload.type: "token"` с `requestId: "join-1"`.
2. Проверить, что `callId`, `topic` и `seq` соответствуют ожидаемому звонку.
3. Подключить SDK к полученным `url` и `token`.
4. Перейти из входящего UI в состояние подключения, затем разговора.

Отдельного `ctrl 200` для `join` нет: ответ с токеном и есть успешный результат.
Исходный таймер приглашения не должен завершать уже принятый звонок.
После нажатия «Ответить» отслеживайте результат команды; при потере ответа сверяйте
`status`, а не предполагайте, что принятие состоялось.

Если пользователь уже нажал «Отменить» или получено завершение, не подключайтесь
по запоздалому ответу с JWT. Сверьте состояние и при необходимости отправьте `leave`.

## 7. Отклонение, отмена и завершение

### Одна команда `leave`, разные пользовательские действия

```json
{
  "note": {
    "topic": "usrPeer",
    "what": "call",
    "event": "hang-up",
    "seq": 123,
    "payload": {"action": "leave", "requestId": "leave-1"}
  }
}
```

Используйте её, когда пользователь:

- отклоняет входящий личный вызов;
- отменяет свой исходящий вызов;
- завершает личный разговор;
- выходит из группы, не завершая разговор остальных;
- отказывается от группового приглашения, ещё не войдя в разговор.

В локальном UI сразу прекращайте звонок/рингтон и освобождайте медиа, если пользователь
завершает участие. При этом отслеживайте результат команды, чтобы ошибка сети не
оставила неопределённое состояние. Отключение SDK само по себе не заменяет `leave`.

Пример подтверждения:

```json
{
  "ctrl": {
    "id": "leave-1",
    "topic": "usrPeer",
    "code": 200,
    "text": "ok",
    "params": {
      "type": "ack",
      "requestId": "leave-1",
      "action": "leave",
      "callId": "663e26ca-50cc-5965-8478-12ff882d1968",
      "seq": 123,
      "state": "ended"
    },
    "ts": "2026-10-16T12:01:00Z"
  }
}
```

`params.state`:

- `applied` — действие выполнено, например выход одного участника из группы;
- `ending` — завершение принято; не нужно держать локальное медиа включённым;
- `ended` — звонок завершён.

### Завершить группу для всех

Показывайте действие при `status.canEnd: true`:

```json
{"note":{"topic":"grpTeam","what":"call","event":"hang-up","seq":123,"payload":{"action":"end","requestId":"end-1"}}}
```

Обычная кнопка «Выйти» в группе отправляет `leave`, а не `end`.

## 8. Быстрый отказ с сообщением

1. Отправить `leave` для отклоняемого входящего вызова.
2. Получить результат; при ошибке не считать вызов гарантированно отклонённым.
3. Отправить обычный текст в тот же чат:

```json
{"pub":{"id":"quick-reply-1","topic":"usrCaller","content":"Не могу говорить, напишите сообщением"}}
```

Доступные фразы можно хранить в приложении:

- «Не могу говорить, напишите сообщением»;
- «Перезвоню через 10 минут»;
- «На встрече, отвечу позже».

Это две независимые операции. Ошибку отправки текста обрабатывайте как для обычного
сообщения. Не отправляйте `head.webrtc` с текстовым ответом и не создавайте статус
`rejected_with_message`: такого статуса в контракте нет.

## 9. Групповой звонок

### Создать

```json
{"pub":{"id":"group-start-1","topic":"grpTeam","head":{"webrtc":"started","aonly":false},"content":"Видеозвонок"}}
```

Дальше действуйте как при личном исходящем: получить `seq` и JWT, подключить SDK.
В запросе нет списка выбранных пользователей. Лимит берите из
`hi.ctrl.params.calls.maxParticipants`.

`groupNotifications: "notify"` означает уведомление о начале разговора без массового
входящего вызова. При `"ring"` приглашение показывается как входящий звонок.

### Присоединиться к уже идущему

1. Подписаться на группу.
2. Выполнить `status` из следующего раздела.
3. Если есть подходящий активный звонок, взять его `info.seq` и `payload.callId`.
4. Отправить `join` с этим `seq` и подключить SDK по ответу.

Истёкший исходный `expiresAt` не запрещает вход в уже принятый групповой звонок.
Но приглашение со `state: "expired"`, которое ещё никто не принял, принимать нельзя.

Состав реально подключённых участников и их треки берите из LiveKit SDK.
`status.participants` не гарантирует, что все перечисленные пользователи уже подключены.
Событие `accepted` не является полным потоком входов/выходов участников группы.

## 10. Запрос состояния `status`

```json
{
  "note": {
    "topic": "usrPeer",
    "what": "call",
    "event": "accept",
    "seq": 0,
    "payload": {"action": "status", "requestId": "status-1"}
  }
}
```

`seq: 0` означает поиск текущего звонка чата. Пример ответа для принятого звонка:

```json
{
  "info": {
    "topic": "usrPeer",
    "what": "call",
    "event": "accept",
    "seq": 123,
    "payload": {
      "type": "status",
      "requestId": "status-1",
      "provider": "livekit",
      "active": true,
      "state": "active",
      "participation": "this-session",
      "callWaiting": true,
      "waitingAction": "end-and-accept",
      "callId": "663e26ca-50cc-5965-8478-12ff882d1968",
      "version": 4,
      "expiresAt": "2026-10-16T12:00:30Z",
      "room": "fc-example-room",
      "originator": "usrMe",
      "created": "2026-10-16T12:00:00Z",
      "accepted": "2026-10-16T12:00:05Z",
      "connected": "2026-10-16T12:00:06Z",
      "ending": "",
      "audioOnly": true,
      "group": false,
      "canEnd": true,
      "participants": ["usrMe", "usrPeer"]
    }
  }
}
```

| `state` | Что делать клиенту |
|---|---|
| `idle` | Активного звонка в чате нет; `info.seq` равен 0; закрыть устаревший экран |
| `ringing` | Ожидание первого ответа; учитывать срок приглашения |
| `expired` | Непринятое приглашение истекло; не подключаться |
| `connecting` | Приглашение принято, первое медиасоединение ещё не подтверждено |
| `active` | Медиасоединение ранее устанавливалось; текущую связь проверять по SDK |
| `ending` | Закрывать UI и отключать SDK; не запрашивать вход |

`active: true` само по себе не означает разговор: используйте `state`.
`expiresAt` — срок исходного приглашения, не срок JWT и не время завершения принятого звонка.
`accepted`/`connected` до наступления события могут содержать `0001-01-01T00:00:00Z`.

`participation`:

- `none` — звонка нет;
- `not-joined` — текущий пользователь не допущен к этому звонку;
- `this-session` — допущена текущая Finchat-сессия;
- `other-session` — допущена другая Finchat-сессия пользователя.

Если `callId` из ответа отличается от локального, это уже другой звонок в том же чате.
Не переносите автоматически на него запоздалую команду завершения старого звонка.

## 11. Ожидающий второй вызов

Входящее приглашение из другого чата имеет обычный `event: "invite"`. Отдельного
`event: "waiting"` нет. Приложение определяет ожидание по своему текущему разговору.

1. Сохранить второе приглашение отдельно по его `callId`.
2. Показать экран/элемент ожидающего вызова, не отключая текущую комнату.
3. «Отклонить» — отправить `leave` только для `topic/seq` ожидающего вызова.
4. «Завершить и ответить»:
   - отправить `leave` для текущего участия;
   - дождаться подтверждения либо сверить `status` после потери ответа;
   - отключить прежний LiveKit SDK connection;
   - убедиться, что ожидающий вызов не закрыт/не истёк;
   - отправить `join` ожидающего вызова и подключиться по новому JWT.

В группе `leave` не завершает разговор остальных. Если выход не подтверждён,
не запускайте автоматически второе медиасоединение.

Не переносите таймер или последнюю версию уведомления одного звонка на другой.
Срок ожидающего приглашения не продлевается. Удержание и кнопка «Удержать и ответить»
этим контрактом не поддерживаются.

## 12. Потеря сети, возврат в приложение и несколько устройств

### Пропала сеть, SDK пытается переподключиться

- Показывайте состояние восстановления по событиям LiveKit SDK.
- Не отправляйте новый `pub` и не вызывайте `resume` только из-за сетевого сбоя.
- Истечение исходного JWT не является причиной отключать уже работающий разговор.
- Если SDK окончательно потерял соединение, восстановите Finchat и запросите `status`.

### Нужен свежий JWT, Finchat-сессия та же

Повторите `join` для того же `topic/seq` с новым `requestId`.
Придут новая JWT-строка, та же комната и та же `identity`.
Используйте JWT сразу для нужного подключения; не обновляйте его таймером каждые
60 секунд ради уже работающего SDK-соединения.

### Finchat-сессия изменилась

После входа и восстановления подписки запросите `status`.
При `other-session` не считайте это безусловной командой забрать вызов:
пользователь действительно может разговаривать на другом устройстве.

Если требуется осознанно продолжить/перенести этот звонок в новую сессию:

```json
{"note":{"topic":"usrPeer","what":"call","event":"accept","seq":123,"payload":{"action":"resume","requestId":"resume-1"}}}
```

Ответ — `type: "token"`. **Предыдущее участие отключается**, `identity` меняется.
Если медиасоединение этого устройства продолжает работать несмотря на reconnect Finchat,
не переносите его автоматически без необходимости.

### Приложение запущено по push

1. Обработать системное входящее событие и локальную дедупликацию.
2. Восстановить соединение Finchat, выполнить `hi`, `login`, подписки.
3. Запросить `status` для чата из приглашения.
4. Сверить `callId`/`seq`; закрыть устаревшее приглашение при несовпадении или отсутствии звонка.
5. При нажатии «Ответить» выполнить `join`, не используя JWT предыдущего звонка.

## 13. Общий обработчик событий звонка

Не считайте каждый `info.event: "accept"` токеном:

- `payload.type: "token"` — приватный ответ на start/join/resume;
- `payload.type: "status"` — приватный ответ состояния;
- `payload.event` — асинхронное уведомление.

| `payload.event` | Действие приложения |
|---|---|
| `invite` | Показать входящий или групповое уведомление по `ring` |
| `accepted` | Инициатору прекратить ожидание ответа, перейти к подключению |
| `answered_elsewhere` | Закрыть входящий этого callId на других устройствах; не отправлять автоматический hang-up |
| `declined` | Закрыть отклонённое приглашение этого пользователя; групповой разговор не завершать |
| `left` | Закрыть локальное участие в групповом звонке |
| `cancelled` | Закрыть соответствующий входящий/исходящий UI; при неоднозначности активного участия сверить status |
| `ended` | Закрыть соответствующий разговор и отключить SDK |

`answered_elsewhere` нельзя использовать как повод завершать чужое или уже работающее
локальное медиасоединение без проверки. Это уведомление о закрытии приглашения.

Для итоговых уведомлений учитывайте `reason`:

- `declined` — отказ от личного приглашения;
- `missed` — закрытие без ответа; отмена инициатором и таймаут не различаются отдельным кодом;
- `finished` — завершённый принятый звонок;
- `disconnected` — завершение из-за потери соединения.

Причина может отсутствовать. Не стройте обязательный разбор только на её наличии.
Отказ отдельного участника от группового приглашения инициатору отдельно не сообщается.

### Дедупликация и конкурирующие события

- Один и тот же вызов может прийти через push и Finchat: создавайте один UI по `callId`.
- Храните последнюю применённую версию **уведомлений** отдельно для каждого звонка.
- Меньшую или повторную версию не применяйте повторно. Пропуски версий допустимы.
- Ответы token/status обрабатывайте по `requestId`, отдельно от очереди уведомлений;
  не теряйте ответ с JWT из-за сравнения версий уведомлений.
- Сохраняйте отметку закрытого приглашения, в том числе при перезапуске приложения,
  чтобы запоздалый push не открыл его заново.
- Закрытие приглашения не запрещает осознанное новое присоединение к продолжающемуся
  групповому звонку через status/join.
- Push отмены может задержаться: локальный таймер и последующая сверка обязательны.

## 14. Ошибки и потерянные ответы

Ошибка Finchat выглядит так:

```json
{
  "ctrl": {
    "id": "join-1",
    "topic": "usrPeer",
    "code": 410,
    "text": "call invitation expired",
    "ts": "2026-10-16T12:00:31Z"
  }
}
```

| `ctrl.code` | Действие клиента |
|---|---|
| `400` | Проверить формат команды, event/action и seq; не повторять без исправления |
| `401` | Восстановить авторизацию |
| `403` | Показать отказ в доступе; не пытаться обходить ограничение |
| `404` | Сверить status: звонок мог завершиться или seq устарел |
| `410` | Приглашение истекло; закрыть входящий |
| `486` | Сверить status: звонок уже существует, завершается или участие занято другой сессией |
| `502`, `503` | Временная недоступность; после восстановления сверить status |

`486` не означает автоматически «собеседник разговаривает в другом чате»:
для этого предусмотрен ожидающий вызов.

Все новые `note` отправляйте с уникальным `payload.requestId` длиной до 128 байт UTF-8.
Ответы `ctrl` сопоставляйте по `ctrl.id`, приватные `info` — по `payload.requestId`.
Для `pub` используйте `pub.id`. Команды без requestId поддерживаются для старых клиентов,
но на `ringing/leave/end` тогда не будет дополнительного подтверждения.

`requestId` не обеспечивает идемпотентность. Если ответ потерян, не повторяйте
изменяющую состояние команду вслепую. После `status` убедитесь в том же `callId/seq`
и примите решение о следующем действии. Повторное завершение уже закрытого звонка
может вернуть `404`, а не повтор предыдущего подтверждения.

## 15. История звонков в чате

Клиент отправляет только начальный `pub` с `head.webrtc: "started"`.
Не публикуйте самостоятельно итоговые `accepted`, `finished`, `missed`, `declined`.

Сообщения приходят обычным потоком `data` и доступны в истории. Пример:

```json
{
  "data": {
    "topic": "usrPeer",
    "from": "usrCaller",
    "seq": 125,
    "head": {
      "webrtc": "finished",
      "aonly": true,
      "call-notifications": "v2",
      "livekit": {"room": "fc-example-room"},
      "replace": ":123",
      "webrtc-duration": 42000
    },
    "content": "Аудиозвонок"
  }
}
```

- `replace: ":123"` связывает обновление с исходной записью звонка; обновляйте её
  отображение, а не показывайте каждую смену статуса как новый независимый звонок.
- `webrtc-duration` — миллисекунды; поле может отсутствовать, если соединение не состоялось.
- Возможные статусы: `started`, `accepted`, `finished`, `missed`, `declined`, `disconnected`.
- Итоговый `busy` для этого протокола не приходит.
- Не открывайте входящий UI по `data.head.webrtc` для сообщений с `head.livekit`
  и `call-notifications: "v2"`. Используйте только приглашения.

## 16. Минимальный порядок реализации

1. Общий обработчик call-событий и состояние по `callId`, сопоставление requestId.
2. Исходящий аудиозвонок: sub → pub → JWT → SDK → leave.
3. Входящий в открытом приложении: invite → ringing → join → SDK.
4. Отказ, отмена, таймаут, завершение и история чата.
5. Push Android и регистрация PushKit/CallKit iOS.
6. Видеозвонок и управление микрофоном/камерой средствами SDK.
7. Группа: создание, поздний вход, leave, доступный пользователю end.
8. Ожидающий вызов и «завершить и ответить».
9. Reconnect, несколько устройств, запуск по push и гонки событий.

### Что проверить перед передачей в тестирование

- Дубликаты invite через push и Finchat создают один входящий экран.
- Просроченный push и push старого callId не открывают новый разговор.
- Отмена одновременно с ответом не приводит к подключению по запоздалому JWT.
- Отказ/завершение ожидающего вызова не закрывает текущий разговор.
- Ответ на одном устройстве закрывает входящий на остальных без завершения разговора.
- Выход из группы не завершает её для других участников.
- Потеря ответа на leave не запускает автоматически второй разговор.
- Смена сети и переподключение Finchat не создают новую комнату через повторный pub.
- Разговор дольше 60 секунд не отключается клиентским таймером JWT.
- Входящий при заблокированном экране и запуске приложения из завершённого состояния
  проверен на реальных iOS/Android устройствах, включая медленную сеть.
- Ошибки доступа к микрофону/камере и недоступность сети не оставляют зависший системный вызов.

Для реализации этого клиентского сценария вызывать webhook LiveKit не нужно.
